# MemCore：设计思路与视频讲解底稿

更新日期：2026-09-24。结合当前实现、生产实测与实验整理。

本文用于项目介绍、视频策划与口播改写。下文故事是视频演示构思，机制以公开 API 契约为准，效果以实验与生产记录为准。更系统的架构哲学与技术亮点见 [设计亮点与架构哲学](design_highlights_v1.md)。

新增的窗口与缓存动机，以及包含具体例子、图解和逐段口播的四分钟方案，见 [视频分镜 V2](video_storyboard_v2.md)。本文保留设计总览与较短的讲述版本。

## 1. 先让人明白它解决什么

**让 AI 接着聊，也接着做事。**

你和 AI 聊了一阵，又让它查资料、写方案。几轮工具调用后，大量结果涌进上下文。事情做完、回复收到，你接着聊日常，或者开始下一件事。

MemCore 面向的核心场景是：多数已完成任务的长工具结果，在交付后通常不再需要全文重读。执行期间的原文已经帮助模型完成了推理与任务，后续继续携带全文只会无谓挤压注意力与上下文空间。即使用户追问，最终回复或当前可见信息通常已经足够，不需要反复重读工具原文。

MemCore 从长期记忆发展为记忆与上下文内核，就是为了管理这种变化：**平时少占上下文，需要时仍能找回。** 做事时提供完整结果；成功结束后按策略收起长正文；日后少数需要核对原文的问题，仍有回读入口。

它把对话、事件、工具调用和结果放进有时间与来源关系的历史；让旧经历逐步沉淀，并提供目录、摘要和原文的读取入口。模型负责根据问题选择怎么找、读多深，宿主负责执行工具和组织任务。

可以用“工作台与档案”解释：上下文是模型眼前的工作台，持久化历史是可查询的档案。收起桌上的长资料后，仍要留下足以认出资料、找到原件的线索。

## 2. 用一个连续故事串起机制

演示设定：用户正在和一个陪伴型助手准备社区活动。先有个人安排，再有资料任务，之后继续日常聊天和独立的新任务。主线展示不需要回读时的上下文驻留变化，结尾用一次旧版细节追问展示回读入口。所有人物、时间、资料均使用明确标识的演示数据；一段视频的剧情比例不代表真实使用频率。

| 发生了什么 | 画面重点 | 观众应当理解什么 |
| --- | --- | --- |
| 用户说：“周六上午我要陪家人，活动安排尽量放下午。” | 对话旁显示时间与发言人 | 日常聊天也是后续任务的背景 |
| 用户让 AI 读取两份长资料，整理活动方案 | 实际工具调用、参数、结果页，随后给出方案 | 正在做事时，模型需要充分的证据 |
| 当前回合成功完成，启用的终局结算策略生效 | 长结果收起为结算卡片（带 `source_id`）；调用与参数仍可见；短反馈保持原样 | 占用变少，原文和回读入口仍在 |
| 用户继续聊日常、处理不依赖旧资料的新任务 | 后续实际请求里的旧结果已变为卡片；记录是否出现不必要回读 | 常规收益来自降低后续驻留，无需不断召回才能体现价值 |
| 用户询问最终回复已经讲清的安排 | 从现有可见内容直接回答 | 追问不等于需要重读旧工具原文 |
| 可选片尾：用户追问“最初那版资料写的交接地点在哪里？” | 先定位历史，再打开对应原文；旧版与现版明确区分 | 少数确需旧原文的问题仍有读取入口 |
| 若发生回读，回答后长正文又被收起 | 回读结果变成新的可回读记录 | 特殊读取结束后，也可以回到较小的驻留表示 |

主线应展示多次后续请求里长结果减少驻留的实际变化，而不是只比较刚收起时的一张截图。若同期 full 已进入 raw 压缩，应记录其真实表示，不能一直按原始全文大小累计节省。实际发生的不必要回读也须记录。

片尾恢复演示中，旧版交接地点应只存在于留存的旧结果中；当前资料服务返回新版，摘要不应直接包含被追问的旧字段。录制时确认模型初始请求里确实没有答案，随后实际调用读取工具找到它。若答案已经在可见上下文中，展示的是直接作答，不能标成隐藏细节召回。

## 3. 值得讲透的设计联系

### 3.1 为常规情况减少驻留，为少数需要留下入口

任务过程中，完整结果有当前价值。回合结束后，许多结果已经完成了本次用途；后续没有使用它们的请求，可以只携带较小的卡片。减少这部分重复驻留，是终局结算机制的核心收益。

保留原文和回读入口，让这种取舍不必以准确预测全部未来问题为前提。需要原文时才承担相应读取开销，不必为了可能发生的追问，在每个后续请求中继续携带长正文。代码以 turn 成功完成为边界，不自动判定整个用户任务客观完成。

当前实现中，终局卡片由确定性规则生成，不调用另一个模型重新概括正文。原文能恢复，是因为仍被保存；语义摘要本身仍然有损。

### 3.2 调用记录让模型认出来，卡片 ID 让模型找得到

“这里有一个结果 ID”只提供地址。工具名、当时的查询参数和调用关系，帮助模型区分多份相似结果：这份查的是初版，那份查的是更新后的资料。

二者组合，既给出辨认线索，也给出精确读取入口。更早的调用随后仍可能进入统一 raw 压缩，完整参数不会永久占据可见上下文。

还有一个适合演示的区别：**重新执行工具得到的是现在的结果，读取历史得到的是当时的结果。**资料更新后，“你当时为什么这样建议”需要核对旧证据。是否因此提高模型选择正确记录的概率，仍需单独验证。

### 3.3 时间既提供参照，也提供查找路线

“上周二我们谈过的安排”本身就包含定位线索。模型可以按时间读记录，也可以先浏览较宽时间跨度的摘要目录，挑中相关节点后再展开。

这让记忆具有多条入口：模糊描述可以检索，明确日期可以查时间线，记得大致阶段可以翻目录，已有 ID 可以直接打开。某次相似度检索没找到，不必立刻把“没搜到”理解为“没有保存”。

目录卡片也不只是标题：时间范围、主题提示、来源数量等帮助模型判断要不要继续读。大跨度目录仍按页返回。

这里的可靠时间锚来自宿主记录与时区；源记录范围由代码继承。“今天说上周发生了一件事”中的事件日期，仍需要正确理解话语。

### 3.4 三层沉淀与逐步展开，回答的是两个问题

| 机制 | 回答的问题 | 直观例子 |
| --- | --- | --- |
| 原始记录 → 阶段摘要 → 长期记忆 | 旧经历随着积累，平时以什么形式保留在眼前？ | 当时怎样商量 → 这一阶段做了什么 → 跨阶段仍有意义的事实与线索 |
| 目录卡片 → 正文 → 来源 | 为了回答眼前的问题，现在需要看多细？ | 先看主题 → 读摘要 → 核对当时原话 |

第一条管理历史的沉淀，第二条管理本次阅读的深度。渐进披露的价值不必依赖“三”这个层数来证明。

第三层可讲成“从不同阶段的经历中，提炼持续有意义的认识”，包括稳定事实、反复主题和待续线索。它的独立价值还需要比较两层与三层，尤其要检查状态更新是否把已经取消的事项继续保留下来。

### 3.5 翻出来的记忆，也是一段需要管理的新经历

读旧资料产生的结果，和读外部工具产生的结果，都可以作为当前轮的 observation 保存，并在本轮成功完成后按同一策略收起。

因此，一次长篇记忆回读结束后，不必让整个正文一直留在后续上下文里。用户继续追问时，再沿已有线索展开。

还有一个较隐蔽的作用：系统区分“当时发生的事”与“今天读取了那件事”。操作摘要默认属于显式读取的轨迹，不进入普通长期语义沉淀。这有助于避免把每次查记忆都重新当成一件普通新事实；它不保证消除对话中的所有重复或错误归因。

### 3.6 工具结果的体积，会影响聊天记忆何时退出眼前

工具任务可能在短时间内产生远多于闲聊的文本。启用终局结算后，raw 压缩规划会采用收起后的历史投影体积，因此长结果减少驻留，可能延缓其他近期对话进入摘要。

这是“陪伴聊天与工具任务共存”的一个具体实现联系。实际能多保留多少近期对话、是否改善体验，属于可测量的假设。

底层压缩也有一项对应取舍：token 衡量压力，完整轮次和工具关系决定切点。可以通俗地说：**按容量决定什么时候整理，按完整经过决定从哪里分开。**

### 3.7 留出增长空间，减少频繁改动历史头部

在底层设计中，Raw 成批压缩、摘要达到触发数量后合并一批，核心考虑是前缀缓存（Prefix Caching）友好性。窗口满后每新增一点就驱逐一点旧内容，会导致头部高频震荡；留出较低水位到上限之间的弹性增长空间（迟滞水库模型），能让中间许多请求只向尾部追加。

以摘要 5~10 条弹性区间为例，在达到 10 条触发压缩前，中间新增的摘要仅在尾部追加，约每 5 轮才更替一次摘要头部，前缀失效频率被大幅稀释为 $\frac{1}{\text{Max} - \text{Min}}$。

在实际生产环境中，系统录得约 97%~98% 以上的输入前缀缓存命中率（统计口径为“命中输入 tokens 总和 ÷ 总输入 tokens 总和”）。窗口动态展示正是为了具象化解释这种减少前缀变动的工程动机。当前默认可见摘要上限为 8，详见 [分镜中的实现核对与缓存图解](video_storyboard_v2.md)。

## 4. JSON 输出值得怎样解释

可以这样讲：

> AI 正在理解你这句话并准备回答，顺手为这次输入留下人物、主题等查找线索，以后再找时就多了一条依据。

可选的最终 JSON 输出同时提供用户可见的 `speech` 和记忆标注 `memory_metadata`。标注目标是宿主选定的用户消息或触发事件，不是把 assistant 自己的回答当成该输入的事实。

这复用当前聊天模型的理解，不强制每轮额外调用一个标注模型；摘要阶段仍有模型调用。标注能辅助检索，不能保证正确；缺失标注也不会让普通记录失去默认读取资格。流式接入可以先解析并展示 speech。

视频里适合把它表现为一句回复旁出现几枚查找标签，不必先展示一屏 JSON。需要进一步说明时，再介绍写入标注与读取过滤如何配合。

## 5. 约三分钟的视频结构

建议标题：**《AI 做完任务以后，那些工具结果该放在哪里？》**

封面短句：**聊得下去，也做得下去。**

| 时间 | 内容 | 画面建议 |
| --- | --- | --- |
| 0:00–0:20 | 抛出日常问题：资料已经查完，方案已经交付，接下来还要继续聊天和做其他事 | 同一聊天中，日常消息与长工具结果交替出现 |
| 0:20–0:55 | 介绍执行中的完整结果，以及回合结束后的有条件收起 | 保留调用与参数，长正文变卡片，短反馈保持原样；标明演示已启用该策略 |
| 0:55–1:40 | 用户继续聊日常、完成独立的新任务；旧正文保持收起，已有答案够用时直接回复 | 对比后续实际请求的旧结果驻留量；计数标清 bytes 或 tokens，记录实际回读情况 |
| 1:40–2:15 | 将同一个思路延伸到聊天记忆：近期保留细节，旧经历逐步沉淀，需要时按时间和目录阅读 | 展示近期对话、阶段摘要和时间目录；不安排每轮都翻记忆 |
| 2:15–2:35 | 用一次确需旧版细节的追问，简短展示原文读取入口 | 实际定位并读回旧证据；片尾标注为恢复能力演示 |
| 2:35–3:00 | 回到产品愿景：让长期聊天与任务历史可以继续使用；交代已有机制演示与待验证效果 | 项目名、演示入口、源码入口；不放未经验证的竞品胜率 |

宣传主片先讲完成任务后的常规驻留收益，恢复能力用于说明这项取舍仍保留回头查证的路。配置默认值、四个 API 名称、metadata 枚举和数据库结构适合放后续技术讲解。

### 可直接改写的短口播

> 和 AI 聊天时，你可能刚说完周末的安排，下一句就让它查资料、写方案。
>
> 几轮工具调用下来，上下文里已经塞进了大量结果。做事的时候，这些内容很重要。可方案已经写完，你要继续聊天、处理下一件事了，之前读过的长资料，还需要一直摊在眼前吗？
>
> MemCore 的思路是：平时少占上下文，需要时仍能找回。
>
> 开启对应策略后，执行中的结果完整提供给模型；回合结束，符合条件的长正文变成卡片。接下来不需要旧原文，就直接继续。调用和参数保留着，偶尔要核对旧细节，也能沿卡片里的 ID 找回当时的结果。
>
> 聊天记忆也有类似的阅读方式。先按时间看看发生过什么，需要时读摘要，再往下核对原话。查记忆产生的长结果，之后也可以收起来。
>
> 我最初想做一个长期记忆系统，后来发现，同样的思路也可以管理工具和事件。现在我想探索的是：让 AI 在一段持续的会话里，接着聊，也接着做事。

## 6. 表述准确性对照

制作与审核时的措辞参照。左列是听起来顺口、但会超出实现边界的简化说法，右列是同一件事在契约层面的准确表述。技术细节放说明页，口播只取其中最必要的一条。

| 常见简化说法 | 契约层面更准确的表述 |
| --- | --- |
| 做完任务后工具结果默认全部变卡片 | 需启用 `compact_after_terminal`；默认保留完整结果直到 raw 压缩。代码以 turn 成功完成为边界，不判断整个任务客观成功 |
| 只要原文比卡片长就替换 | 默认正文小于 256 UTF-8 字节直接保留；其余结果只有卡片严格节省超过 50% 字节才替换。门槛可配置 |
| 无限长工具轮也不会爆上下文 | 开放轮不提前做终局卡片化。内建读取有相应分页，第三方工具需宿主实现；单个过大单元、累计页面和完整请求仍需预算 |
| 默认 24,000 tokens，压前 67% | 24,000 可作为演示配置；包默认阈值为 12,000。计划量是 `ceil(阈值 × 0.67)`，实际按完整已结束轮次及关系边界对齐，不是任意积压总量的固定 67% |
| 摘要达到 10 条后处理前 5 条 | 符合当前默认值；可见摘要上限另为 8，三者是不同配置 |
| 三层内容完全不重叠，看到摘要就不用检索其原文 | 系统减少可见重复；已经看到概要仍可检索未见细节。摘要与原文的来源联系有意保留 |
| 所有时间都绝对可信 | 来源时间范围由代码从记录计算，前提是宿主时间正确；话语中的事件日期仍可能被误解 |
| 压缩后必然更省钱、更准确 | 可以展示指定结果的体积变化与实际回读；整段请求、总费用和回答质量需要分别测量 |

所述实验为特定宿主上的长程合成压力流程，其脚本与运行记录不属于公开仓库内容，因此本节只保留结论与边界，不提供外部链接。

若引用约 81% 的缩小数据，必须说明只比较实验中两份固定工具结果的 JSON UTF-8 payload。同组总成本约高 3.7%，是该合成压力流程下的描述性结果；实验专门安排版本变化、隐藏细节探针、强制的长干扰输入与重启，没有采样真实使用中旧工具正文的重读频率。这个数字不能用于估计常规使用的平均收益，也不能直接归因于回读，因为模型路径、格式修复、压缩和缓存均有差异。

视频主线展示：**任务完成 → 长结果收起 → 后续交互无需旧原文时持续减少驻留。** 片尾再展示确有需要时的回读路径。分别衡量日常驻留与特殊恢复，避免把少数回读的压力用例当成整个产品的使用方式。后续评估设计应覆盖版本变化、隐藏细节探针、强制长干扰输入与重启恢复四类场景。

市场对比适合围绕持续会话中的具体行为展开：工具轮何时收起、旧结果怎样回读、时间如何定位、找不到时有哪些继续查的路。分层记忆与按需读取各自已有实践，不能只凭这些词声称 MemCore 独有，也不能把设计时考虑的取舍说成所有其他系统的缺陷。

首章现已有 [亮色有声第三版](video_assets/garden_trial/exports_v3/memcore-light-dania-v3.mp4)，约 66 秒；以 [重写后的口播](video_assets/garden_trial/script.md) 为当前文案基准。作者选择干净亮色，要求自然讲述，正式画面去掉“素材样片”、页码等制作说明。第二版补足路线图、聊天轨迹与资料对应关系；第三版根据作者提供的视频截图，进一步调整宋体标题、黑体正文、等宽编号与纸张层次，配音沿用。全片下方口播仍是早期分镜草稿，后续按首章方向逐段重写，最终长度以实际配音为准。素材与示例来源写入视频简介，必要机制条件留在对应画面。

## 1. 主片怎么讲

建议做约 **4 分钟的中文讲解视频**：同一段聊天贯穿，实际界面与机制图解交替出现。前半段展示做事后继续聊天，后半段解释为何成批整理历史，最后用一次简短回读收尾。

建议标题：**《AI 查完资料后，那一大段上下文怎么办？》**

封面短句：**做完接着聊，历史有处放。**

全片让观众记住三件事：

1. 任务完成后，暂时不用的长结果可以收起，后续少占上下文。
2. 历史留出增长空间，平时追加，积累到阈值再成批整理，减少头部变化。
3. 偶尔需要旧细节时，仍能沿时间、目录和 ID 找回原文。

不要以 API 列表或三层结构图开场。先让观众看到一个具体问题，再展示解决过程，机制名称随对应画面出现。

## 2. 一个例子用到底

演示数据：用户准备周末去杭州，之前聊过“周六上午有安排，不想把行程排太满”。随后让 AI 查两份景点资料，整理周六下午的行程。

查到的长资料帮助 AI 完成行程。最终回复已经包含推荐路线和主要理由。后续用户先聊晚饭，再让 AI 写一段无关的小脚本，最后问行程里的出发时间；这些问题不应为了展示记忆而强制读取旧工具正文。

片尾才安排一次确需旧原文的追问，例如：“你当时看到的旧版预约说明里，取票截止时间是多少？”这个字段应确实存在于当时留存的工具结果中，且没有在当前可见回复或摘要里直接出现。虚构资料明确标为演示数据，避免把合成规则当成真实景点信息。

## 4. 三组图解怎样画

### 图解 A：完整使用，然后收起

同一条工具轨迹固定在屏幕上，只改变正文展示量。工具名、参数与调用关系保持原位，让观众认得出这是同一次操作。

```mermaid
flowchart LR
    A[开放工具轮<br/>调用与参数 + 完整结果页] --> B[本轮成功完成]
    B --> C[符合门槛的长正文收起<br/>调用与参数 + 原文 ID 卡片]
    C --> D[普通后续聊天或新任务<br/>不需要原文就直接继续]
    C -. 确实需要旧细节 .-> E[沿 ID 读取留存原文]
```

画面角落标注“已启用终局结算”。结算卡片缩小的是默认展示，不表现为把原文删掉。正文变成卡片的动画应在最终回复成功完成后发生，开放工具轮里不提前收起。

### 图解 B：同样的上限，不同的头部变化频率

先用原始对话，后用摘要；每次只讲一个区域。块上的 R1、R2 或 S1、S2 是示意编号，帮助观众辨认内容有没有移动。

| 原始对话图 | 固定满额窗口 | 成批整理窗口 |
| --- | --- | --- |
| 增量步骤 | 到达 24k 后，每新增一个单元就移除最旧单元 | 从约 8k 继续追加，直到约 24k 再整理 |
| 整理发生 | 满额后每个增量步骤都改变头部 | 达到阈值时集中改变头部 |
| 当次留下的 raw | 持续维持约 24k | 整理后约 8k，之后继续增长 |
| 图的比较范围 | 比较头部变化，不据此宣布保留信息量、任务质量或总费用相等 | 较早信息已由摘要接替；示意省略摘要正文 |

摘要图的理想状态序列：`5 → 6 → 7 → 8 → 9 → 10 → 合并前 5 → 5`。在稳态、每次新增一条且每次恰好合并五条的条件下，每五条新增摘要触发一次合并。

色彩只表达两种状态：相同前缀是可复用候选；从首次变化处往后需要重新匹配。不能把本地相同前缀直接标成服务端已命中。相同文字如果前面不同，也不能仅因内容相同涂成命中。

### 图解 C：变化位置决定影响范围

采用当前 provider projection 的层级顺序，宿主稳定内容在前、动态时间等信息放在后部。下图是用于讲解的宿主请求排列，不代表所有接入适配器都自动采用相同顺序。

```mermaid
flowchart LR
    A[稳定规则与工具定义] --> B[长期记忆] --> C[阶段摘要] --> D[近期原始对话] --> E[当前动态输入]
```

| 此次发生的变化 | 可以保留的早期前缀 | 从哪里开始重新匹配 |
| --- | --- | --- |
| 新对话只接在 raw 尾部 | 未改动的长期记忆、摘要与旧 raw | 新增内容处 |
| raw 压缩，新增阶段摘要 | 新摘要之前未改动的内容与旧摘要 | 新摘要插入处，以及后面的 raw |
| 摘要合并并产生或修改长期记忆 | 更早且未修改的规则与记录 | 被新增或修改的长期记忆处，以及后续内容 |
| 任务后卡片化 | 首个被替换结果之前未修改的内容 | 被替换结果处，以及后续内容 |

这张图解释“尽量少改早期内容”的整体取舍。缓存前缀被改动后的处理是另一个阶段，不能给观众留下“压缩以后缓存完全不受影响”的印象。

## 5. 作者公式怎样讲准确

设摘要触发数量为 H，合并后剩余数量为 L，单次合并 H−L 条：

```text
稳态合并频率 ≈ 1 / (H − L) 次 / 新增摘要
H = 10，L = 5：约每新增 5 条摘要合并一次
```

这个公式描述**摘要头部的成批更替频率**。其条件是可见窗口在触发前不提前驱逐、每次新增一条、维护及时且批次固定；它不是每个模型请求的未命中概率，也不是 token 命中率公式。新摘要每次插入在 raw 之前时，raw 的前缀仍会受影响；更早的长期记忆修改也会影响摘要本身。

原始对话可用同样直觉解释：上限约 24k，集中整理约 16k，留下约 8k。下一次请求里，保留下来的 raw 需要在变化后的前缀下重新处理；旧的约 16k 不再以 raw 全文驻留。新摘要、动态输入和任何更早变化还会产生额外处理，摘要模型读取源材料的工作也另计。因此“约 8k”只描述保留的 raw，不能写成整次请求总共只处理 8k。

降低头部更替频率，为前缀复用提供更长的稳定区间。具体命中率还与每个区间有多少模型请求、各部分长度、其他前缀变化和供应商缓存状态有关。[DeepSeek 的当前缓存说明](https://api-docs.deepseek.com/guides/kv_cache/)要求匹配已持久化的完整前缀单元，并通过 usage 返回命中与未命中输入 tokens；稳定前缀创造复用条件，实际命中仍以 usage 为准。

97% 的口径已由作者确认是：

```text
输入缓存命中率 = 统计范围内命中输入 tokens 总和 / 输入 tokens 总和
```

不取单次请求百分比的简单平均，不把输出 tokens 放进分母。字幕建议：“作者实际使用观察｜输入 token 加权｜模型、日期范围、请求数见说明”。是否包含后台摘要和强化请求也需要在统计范围中说明；不将它写成窗口公式推出的固定结果或所有部署的保证。

## 6. 拍摄前核对当前实现

为了让数字直观，图解可以采用以下**演示配置**，不修改项目默认值：

```python
MemoryConfig(
    raw_token_trigger=24_000,
    raw_token_batch_ratio=2 / 3,
    episodic_visible_max=10,
    episodic_compact_trigger_count=10,
    episodic_compact_batch_size=5,
)
```

当前包默认 raw 阈值为 12,000、比例 0.67；如果仅把阈值改成 24,000 而保留 0.67，计划处理量是 16,080、理想剩余 7,920。实际又会按完整已结束轮次和关系对齐，所以 24k→8k 是近似示意，不是硬下限。

当前包默认 `episodic_visible_max=8`。当第 9 条尚未合并的摘要出现时，可见选择就可能挤掉最旧一条，即使合并阈值仍为 10。要展示“触发之前只在底部追加”的 5→10 过程，可见上限须覆盖这段增长；原生投影把摘要按时间正序排列，但简单文本 `render_prompt_context` 的排列不同。拍摄应核对宿主实际发送的序列，不能只展示数据库条数。

此处识别的是演示前提与当前默认的差异，本次未改变配置或运行时实现。主要依据：[配置](../memcore/config.py)、[可见摘要选择](../memcore/store/sqlite_store.py)、[provider 历史构造](../memcore/memory_system.py)、[简单文本渲染](../memcore/rendering.py)、[压缩规则](raw_token_compaction_policy_v1.md)。

## 7. 制作方式

使用“实际界面录屏 + 可逐步播放的示意图 + 中文口播”。场景切换靠同一条消息、同一次工具调用或同一个记录 ID 连续衔接，减少抽象名词之间的跳跃。画面一次只突出一个变化。

实际界面部分录制开放工具轮、成功回复、正常后续交互、可选原文回读；必要的上下文诊断显示实际请求片段与计数。图解部分用明确标识的合成块说明排序与前缀，不伪装成实测监控。

先按这份分镜录一版无配音的画面草稿，确认变化位置与字幕能对应；再按画面节奏录口播。工具等待可以加速，但保留实际调用先后与状态。97% 的统计范围、演示配置和来源入口放到视频说明里。

**解释范围补充（2026-09-14）：**本实验专门检验压缩、版本变化和重启后的恢复能力，没有测量普通使用中再次需要旧工具原文的频率。原文回读是按需求发生的；没有后续追问，或已有回复与可见内容足以回答时，不需要为展示机制而强制回读。因此，本报告的成本对照仅描述这里的合成压力流程，不用于估计常规使用的平均收益。下面的执行记录、数值、失败和评分均原样保留；新的分层评估建议见 [研究问题与验证方式](../../akane_memcore_design_rationale_and_research_v1.md#5-研究问题与验证方式)。

每条完整轨迹的探针分母为 5。探针分别检查当前负责人和未完成事项、修改后的个人安排、初版识别码和交接位置、未提供的费用，以及最终交接。最后两条保留原计划，不以零次回答伪装成零错误率。

执行使用经哈希核对的真实 Akane 源码副本、既有依赖环境、DeepSeek V4 Flash 和 BAAI/bge-m3 生产 embedding。thinking 关闭、非流式响应；聊天请求保留宿主的 `max_tokens=2048`。模型自主选择资料、方案和记忆工具，正常执行宿主的 prompt 构造、原生工具循环、输出修复、最终提交及后台维护。没有回放真实模型回答。源码指纹为 `ef19b1ef3a04844807c031b079f67674e9fefb35c6ad472949cc07f4645e4b92`，覆盖 392 个文件；依赖二进制没有另行冻结。

两组的 raw trigger 均为 4000 tokens，batch ratio 为 0.67。每条轨迹插入 14 轮长干扰输入，让早期记录退出 raw 可见窗口；在第 20 轮后关闭隔离工作进程，再以新进程恢复同一持久化数据。脚本在用户可见回复返回后等待后台维护安静，再提交下一轮；没有强制压缩或代写摘要。使用真实时间戳，没有实际跨天等待。这是加速的上下文压力和恢复实验，不是数日真实使用测试。完整协议、场景和固定执行次序见 [README](README.md)、[scenarios.json](scenarios.json) 与 [run_manifest.json](run_manifest.json)。

6 条完整轨迹均跨越至少两次实际 raw 压缩，早期 assistant/tool 记录确实退出 raw 可见上下文。初版工具正文经公开 API 渲染后的哈希，在初次保存、压缩后和重启后保持一致；重启后的 provider projection、元数据、状态和方案文件也精确一致，索引预热成功。模型在重启后实际收到旧资料正文，路径包括 timeline 和单条/批量 open，不把研究脚本的诊断读回算作模型使用证据。6 次重启的索引就绪时间约为 4.9–10.5 秒；全部 13 个已启动进程的生产 embedding 预检通过，无 hashed fallback。

旧版探针值得单独限定：6 次都答对了初版字段，且资料服务此时已不再提供初版。5 次的初始模型请求不含两个旧字段的字面值，随后依靠历史回读取得；另 1 次（workshop · full · r2）在第 21 轮自主查过 timeline，因此第 22 轮初始可见上下文已经含有旧值，不能算作全新的隐藏信息召回。当前版本资料仍可通过资料工具重新加载，所以当前任务续作成功本身不独立证明记忆召回。费用缺失探针的原始资料明确写明未提供该字段，6 次均未编造数字；它没有覆盖开放资料集合中更难的“证据不存在”判断。

需要保留的具体失败如下。

1. **个人安排误写入任务方案。**workshop · full · r1 在第 1 轮把个人备忘录和占位成本保存到不可覆盖的 `draft_v1`。第 2 轮真正的项目初版因版本已占用而写入失败，改存 `draft_v2` 又不满足新版检查。后续新版和最终方案正确，但不能把“初版未被覆盖”算作“初版正确”。migration · full · r2 在中断前重现了这一错误，构成第二个方案失败；它独立于随后发生的 usage 中断。
2. **正确回答没有可靠地完成宿主提交。**workshop · card · r1 和 migration · card · r1 的第 13 轮都包含正确的负责人和未完成事项，但分别经过 4 个、5 个最终响应候选仍未满足宿主输出要求，没有成功的公开 `complete_turn` 记录。事实得分保留，交付得分扣除。另有被宿主接受的明文 fallback 带入英语过程说明或格式指令讨论；30 个探针中标记了 6 个沟通问题，作为探索性观察，不混入事实分数。
3. **旧值正确，证据描述仍错误。**workshop · card · r2 第 22 轮准确回答 `XT-284` 和“北侧物资柜”，却声称新版没有这两类字段。实际新版包含 `XT-936` 和“南侧领取台”。因此该题要求的旧事实通过，证据支持和联合成功均不通过。
4. **摘要出现说话人归因错误。**workshop · full · r1 的一条 episodic summary 把 assistant 提出的“是否修订并复查”写成了用户提出。后续个人安排答案依据原始 timeline 仍然正确，但该摘要缺陷不能被最终答对掩盖。另保留了未标为引用的人称口误、要求一句话却多加一段的回复，以及非探针轮中的格式过程说明。

全部 145 个返回 speech 的复核未发现把测试工具通过误称为真实业务已经执行的陈述。工具实际只作用于合成研究资源；没有测试桌面前端、TTS、真实外部业务或提醒调度。个人安排的记忆不能等同于已创建真实提醒。

full/card 的投影差异确实生效。在第 2 轮正常开放工具循环中，两组均向模型提供完整的两份初版资料；最终回复之后，full 仍保留完整 projection，card 转为可重载卡片。只比较这两份固定工具 observation 的紧凑 JSON UTF-8 payload，完整轨迹中 full 平均 5542 bytes，card 平均 1055 bytes，减少约 **81.0%**。这是局部投影体积，不能解释为整段 prompt、计费 token 或总费用下降 81%。原始测量见 [projection_check.json](projection_check.json)。

第三次尝试于 2026-09-06 17:14:43（Asia/Shanghai）遇到停止条件。migration · full · r2 第 2 轮的一次聊天请求设置 `max_tokens=2048`，HTTP 200 响应却报告 `completion_tokens=2049`、`finish_reason=length`。账本以 `usage_tokens_exceed_reservation` 拒绝结算，保留该次预留；后续后台摘要请求被 `pending_reservation_blocks_dispatch` 在 HTTP 之前拦截。没有自动释放、追加重试或继续剩余轨迹。

[DeepSeek Chat Completion API 文档](https://api-docs.deepseek.com/api/create-chat-completion/) 将 `max_tokens` 定义为生成上限，并说明 completion usage 和 `length` 结束原因，但没有解释本次多 1 token 的现象。现有证据不能判定是否与结束标记或供应商计费实现有关。该次原始 usage 按保守费率计算约 ¥0.0194762，低于 ¥3.16416 的财务预留；这个值没有被接受或结算。停止由输出计数边界不一致触发，并非 50 元余额耗尽。

这次中断也暴露了实验 transport 的证据保存顺序缺陷：旧实现先验证 usage，再写入原始 response bytes/hash。因此此次保留了请求原始字节及哈希、已解析响应和 usage，却缺少响应的原始字节及哈希。没有用重新序列化的 JSON 冒充原始 HTTP body。中断工作进程报告 `writer_shutdown_incomplete` 和 `memcore_close_deferred` 后退出；其最终隔离计数快照缺失，不能算作干净关闭或完整隔离验收。已完成的 12 个阶段结束快照中，未授权网络、受限私有读取和外部写入拦截计数均为 0；这个结论只覆盖这些已保存快照。

实验结束后已修正 transport，先保存收到的 response bytes/hash，再校验 usage。回归用 Mock HTTP 复现 2049/2048：旧实现失败，新实现保存精确响应证据，同时保留未决预留并阻止下一次 HTTP。修正没有放宽预算或 token 上限，没有修复过去缺失的字节，也没有再次开展付费试验。第三次付费运行的冻结源码与这项后续修正分开记录。

这轮结果支持在所覆盖场景中继续研究 MemCore 的压缩与恢复机制，同时把改进重点具体化为：约束个人安排误用方案写入工具、提高终答协议提交可靠性、减少证据描述和摘要归因错误。上述行为问题尚未修复；下一次付费运行还需先明确处理未决 usage 的规则，不能靠重置账本绕过。这里保留的是一次有明确失败和停止边界的小规模机制实验，尚未建立多日、多模型或真实业务的长期可靠性结论。

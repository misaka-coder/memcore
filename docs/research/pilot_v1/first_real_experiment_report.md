若只审阅所有原始最终内容，忽略其是否可交付，则 7 项语义正确、1 项部分正确、4 项没有最终答案。这个辅助计数不能替代 5/12 的合格终答结果。full 合格终答为3/6，card 为2/6；样本太少且问题混杂，不作总体优劣判断。

基础任务中，场地 v1/v2 推荐及容量12/10正确，理由来自资料。代码任务识别了“远端发送成功 → 本地标记完成”间故障导致重复的窗口，也承认远端幂等/跨系统原子性约束；v2 没有被误判为已修复。八项任务均未提前列出被禁止的旧/新核验码、交接位置、退避、抖动或重试次数。

核心内容得分与回答范围分开：代码/card 的 v1 任务额外讨论了未要求的 HTTP 超时等缺失字段，范围合规为7/8。它也是后述的缺字段答案暴露来源，因此不把“核心内容8/8”解释为八项任务完全遵循所有指令。

## 5. 失败分析

### 参数错误与恢复失败

实际执行了48次工具：8次成功资料读取、1次成功完整回读、3次合法空检索、4次过期资料拒绝，另32次参数错误。参数错误中，21次混用时间模式、9次 cursor 与其他参数冲突、2次 timeline 选择模式冲突。

四个超限探针分别是场地/card 旧细节、代码/full 缺失字段、代码/card 旧细节及缺失字段。card 三个相关失败均先选对 v1 来源，却把可选 cursor 填为字符串 `"null"`，随后转向时间检索并继续填入互斥模式；六次实际工具后，第七次请求调用被上限拒绝。

发送的 strict schema 要求可选字段也出现，但允许 JSON `null`。因此存在合法填写方式，不能说接口无解；这种写法增加了无用参数和空值选择负担，影响程度仍需消融验证。`strict=true` 是发送配置，不能视为供应商实际强制校验的证明：上述成功调用事实上省略了 cursor，宿主也接受了。另在冻结 dispatcher 的离线诊断中，只把首次失败的 cursor 从字符串改为 JSON `null` 即通过校验；这与真实成功调用省略字段是两项不同证据。本轮保留原始错误，没有让宿主悄悄删除冲突过滤器或扩大搜索。

### 最终 JSON 失败

场地/full 聊天事实、代码/full 聊天事实、代码/card 聊天事实均在 JSON 前输出解释文字。宿主按契约拒绝，没有把残片入库为成功回复。其中两项的原始答案语义正确，另一项存在上述顺序表述问题。

这些探针的所需聊天事实本来就在可见历史中。`retrieve_for_turn` 排除当前已可见内容，返回空集合不表示这些事实不存在。模型在无需查找的场景中尝试检索，遇到参数错误后又把解释带出了 JSON，增加了失败面和调用成本。

### 答案提前暴露

审阅覆盖所有20轮 setup 的 assistant 内容、最终 JSON metadata、工具参数和实际保留的 provider 字段；非思考模式响应未包含独立 `reasoning_content`。

两场景的旧工具数值/位置均未在 setup 的 assistant 输出中提前暴露。日常安排在 intro 中自然复述，是聊天连续性题设计允许的可见证据。代码/card 的 `n_task_v1` 主动说“资料里没有 HTTP 超时……字段”，提前暴露了缺字段探针答案。该探针仍然失败，但已标记暴露，后续也不能把它视为纯粹必须回读正文的测试。

另有评分表之外的质量问题：代码场景的两次 `n_gap_1` 都建议《通知去重复盘》，仍为六字，未比原六字标题更短；card 还误称“四个字比六个字”。它不进入预先指定的八项工具任务分母，但说明“setup 均成功提交”不能解释为所有闲聊指令都完全遵守。

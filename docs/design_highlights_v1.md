# MemCore 设计亮点与架构哲学 (Design Highlights & Philosophy)

> **让 AI 接着聊，也接着做事。**
>
> 本文深入阐述 MemCore 从“长期记忆系统”演变为“通用上下文与记忆内核”的设计动机、核心技术突破与工程取舍。

---

## 核心设计原点：为什么必须从“记忆系统”升级为“上下文管理”？

### 1. 伴随与做事一体化的真实诉求
在传统的 Agent 设计中，“日常聊天”与“工具任务”往往是撕裂的：
* 聊天系统只管记录对话，做向量搜索；
* 工具系统只管跑代码、调 API，输出大段数据。

但在真实的长程人机交互中，用户不会把会话割裂成“任务专用窗口”和“闲聊专用窗口”。用户在聊天的同时，随时会交代 AI 查资料、写代码、排查系统错误；而在任务完成后，用户期待的是**在同一个会话中，自然而然地继续聊天或开展下一步工作**。

### 2. 工具结果治理的三大死穴与 MemCore 的破局
面对工具调用产生的大段输出，业内常见的处理方式无非三种：

| 方案 | 常见做法 | 致命缺陷 |
| :--- | :--- | :--- |
| **方案 A：过河拆桥** | 任务做完后，将工具调用与结果全部从上下文中物理抹去 | **强烈的割裂感**。用户一旦追问“刚才那个报错怎么改的？”或“刚才查到的第二条数据是什么？”，模型当场失忆。 |
| **方案 B：全量囤积** | 将所有工具调用和原始输出无底线保留在上下文中 | **上下文爆炸与注意力涣散**。几万字的日志和 JSON 严重稀释日常聊天的语义权重，导致模型变迟钝，API 费用与延迟激增。 |
| **方案 C：粗暴截断** | 无论输出多长，直接取前 500 字，后面加省略号 | **堵死了回溯的可能性**。看似节省了 Token，但在真正需要核对旧细节时，关键信息已经永久丢失。 |

**MemCore 的破局方案：终局结算（Operation Projection Settlement）**
MemCore 的原则是**不走极端、拒绝一刀切**：
1. **执行期（Open Turn）毫不吝啬**：当模型正在执行多步任务时，原始输出完整保留可见，即使长文本也通过分页由模型自主决策，保证模型在解决问题时拥有充分的信息输入。
2. **终局后（Post-Terminal）结构化折叠**：当任务完成、模型向用户交付最终回复后，后台机制将长工具结果折叠为**带有唯一 `source_id`、时间戳和状态的轻量化卡片（平均仅百 Token）**。
3. **保留调用行为（Call & Arguments）**：模型清晰知道自己当时做了什么、传了什么参数，一旦后续需要核对，立刻能凭借调用记忆反应过来该调用哪张卡片。
4. **具体问题具体分析**：如果工具结果本身极其简短（如 `{"status": "ok"}`），低于卡片开销，系统直接保留原文，**绝不为了压缩而负向优化**。
5. **按需瞬间回溯**：当用户在数天后追问细节时，模型调用 `open_memory(memory_id=..., view="content")`，瞬间把万字原文调回工作台；回答完毕后，该结果**再次遵循结算折叠**，形成完美的自洽闭环。

## 核心技术亮点

### 1. 时间戳作为因果第一等公民（Time as the Backbone）
许多记忆系统将时间戳当成可有可无的外围元数据，而 MemCore 将其提升为**贯穿全局的因果骨架**：
* **治愈时序幻觉**：缺乏时间感的大模型面对堆积的事件时，只知道“发生过”，却分不清“何时发生”、“先后顺序”，极易在多轮对话中时空倒错。
* **时区与星期感知**：系统强制要求有效 IANA 时区（如 `Asia/Shanghai`），自动派生“周一到周日”，并打通三层记忆。摘要提炼时明确要求模型给出事件的时间跨度，系统在底层自动转换为标准化的时间戳。
* 模型在回顾时，能自然结合现实时钟感知（“昨天下午”、“上周二”）精准调取历史，赋予 Agent 真实、细腻的伴随感。

### 2. 三层记忆的真谛：不是为了分层，而是“渐进式披露”
MemCore 的 Raw（原始层）、Episodic（阶段摘要层）、Semantic（长期事实层），不是为了学术炫技而设，而是作为**“渐进式披露（Progressive Disclosure）”的工程梯阶**：

```text
               ┌────────────────────────┐
               │ 1. 标题目录 (Catalog)   │ 跨越数十天的一句话概括，极低 Token 成本
               └───────────┬────────────┘
                           │ 模型判断相关，调用 browse / open
                           ▼
               ┌────────────────────────┐
               │ 2. 阶段摘要 (Summary)   │ 几天或一个事件周期的事实脉络与核心结论
               └───────────┬────────────┘
                           │ 确认需要深挖字句，调用 timeline / open sources
                           ▼
               ┌────────────────────────┐
               │ 3. 原始证据 (Raw Line)  │ 那分那秒的原话、完整参数与执行凭证
               └────────────────────────┘
```
* **高阶筛选**：模型可以传入一个长达数星期的宽时间跨度，先扫一眼几十条极度廉价的标题卡片；
* **按需深入**：通过标题附带的 ID，模型自主选择展开摘要正文，甚至进一步追溯到原始对话或工具凭证；
* **信息检索的同构性**：**查记忆所产生的长工具输出，本身也遵循终局结算！** 查完、答完，记忆凭据立刻在下一轮折叠，绝不让历史检索成为新的上下文污染源。

### 3. Token 做预算指标，Turn 做物理切点
传统压缩常常陷入两难：
* 按条数压缩（Item-based）：消息体量极不均匀，有时 20 条短句没多少字，有时 2 条长代码直接爆仓；
* 按 Token 硬切（Token-based）：机械死板，容易在预算线上一刀切断正在进行的工具对，造成模型接收到残缺语法。

**MemCore 的融合方案**：
* 设置 Token 触发线（如 24,000 Token）与批次比例（如 0.67）；
* 但下刀点**严格对齐到完整的会话轮次（Terminal Turn）或关系组件**。
* 结果是：上下文体积严格受控，同时留下的历史始终保持**“完整的问与完整的答、完整的 Action 与完整的 Observation”**，因果链条绝不破碎。

### 4. 为什么关键词检索比想象的更强大？联合词池、单向子串与多对一汇聚（Keyword Pool & Fan-in Convergence）
很多人第一眼看到 MemCore 用轻量 SQLite 关键词索引替代笨重向量库，会下意识地疑惑：“纯关键词是不是太原始？子串匹配是不是太激进容易搜乱？”
但只要**“往深想一层”**，就会发现这套设计背后极其严密的三个工程闭环：

#### (1) 看似激进的“联合词池（Union Pool）”，实则是深刻的互保容灾
* **单点打标的天然缺陷**：如果只靠原始对话的两句话提取关键词，模型偶尔遗漏元数据就会导致搜空；如果只靠阶段摘要提取关键词，概括往往会丢掉具体的人名、冷门项目名、小众函数等关键细节。
* **双向互保**：MemCore 顺着血缘将**原始对话的实体词**与**阶段摘要的主题词**合并去重，铸造一个联合词池（`get_catalog_keyword_pools`）。原始细节补足了冷门专有名词，阶段摘要提供了高阶概念兜底，显著提升了标签覆盖的容灾韧性。
* **多对一汇聚：为什么底层词池膨胀不会导致上下文爆炸？**：用户在讨论某个话题时往往具有**局部的时序密集性**（一段时间内连续探讨同类事项）。在 MemCore 机制中，数万 Token 的原始对话才会凝练为一个阶段摘要标题。因此，即便某个关键词在底层涉及多次具体对话，在时间轴上通常也只归属于少数密集的事件周期。将命中结果向上回溯到标题层时，**候选量大概率会大幅收敛为数量有限的紧凑卡片**，从而在底层扩大召回网的同时，顶层有效避免了把海量原始对话倾倒给模型带来的“扇出爆炸”。

#### (2) 为什么是“单向子串包含”而不是全等或分词器？
* **打破分词诅咒**：中文与复合专业名词（如 `文旅答辩项目`、`ComfyUI本地部署`、`CET-6核心词`）如果依赖死板的分词器切词，容易发生切分歧义；而如果要求严格的全等匹配，当模型检索“文旅”或“答辩”时，极易因粒度不一致而搜空。
* **信赖模型的智商**：现代 LLM 在查询时天生具有高信息熵感知，绝不可能傻到输入“的”或“了”这种无意义单字；
* **单向子串约束**：系统采用有针对性的**单向包含匹配**（`query in stored_term`）——允许简短的核心查询词定点命中已存的复合长词条，但已存的短标签绝不反向放宽匹配更长的复杂查询。既免去了外挂重型分词库的开销，又能稳妥咬住专有名词的核心词根。

#### (3) 证据回传（Witness）：让大模型做清晰的二阶决策
* 命中的卡片不仅返回标题和时间，还会随附原始证据明细：`keyword_hits: [{"query": "文旅", "term": "文旅答辩项目"}]`；
* 大模型扫一眼标题与命中的真实词条，能够清晰获知“这条记录究竟是命中哪条证据被召回的”，大幅降低二阶研判时的盲目性。这也正是系统敢于让大模型自主决定是否下钻 `open_memory` 的依据所在。

### 5. 检索净空法则（Visible Lineage Exclusion）
大多数 RAG 最愚蠢的失误，是把当前屏幕上已经可见的文本又重新搜出来塞进 Prompt。
MemCore 在检索底层实现了**可见上下文差集排除**：
* 凡是当前 Prompt 中已经可见的近期原始对话、阶段摘要与长期事实；
* **在检索底层强制剔除出候选池**。
* 检索的职责只有一个：**搬运模型视线之外的冰山底层**。桌上已有的文件绝不复印第二份，保持注意力池极致纯净。

### 6. 字节级稳定前缀与双水位线迟滞缓冲（Prefix-Cache-First & Hysteresis Buffer）
为什么很多做了缓存的 Agent，在实际交互中缓存命中率依然惨淡？
因为传统系统普遍采用**固定容量的 FIFO 滑动窗口**（例如固定保留 20 条消息）：每进来 1 条新消息，头部就被踢掉 1 条。而在现代大模型的 Prefix Caching（前缀哈希树）机制中，**头部的微小变动都会导致后续哈希链全部偏移，极易造成前缀缓存的高频击穿！**

MemCore 采用了**最大/最小双水位线的“迟滞缓冲水库（Hysteresis Buffer）”模型**，有效抑制了传统 FIFO 模式的高频缓存失效：
* **摘要层弹性区间 `[Min, Max]`（如 5~10 条）**：
  * 当摘要在 5 到 9 条之间时，系统只做**纯尾部追加（Append-only）**，已有历史在字节级别保持稳定，维持极高的前缀复用率；
  * 只有蓄满 10 条上限时，才一次性压缩前 5 条，回落至 5 条；
  * **缓存失效频率被大幅稀释至 $\frac{1}{\text{Max} - \text{Min}}$**（从每轮都变动，降低为平均多轮才发生 1 次）！
* **Raw 对话层 Token 差值蓄水池（如 8,000~24,000 Token）**：
  * 从 8k 到 24k 之间的整整 16,000 Token 蓄水期，模型处于相对稳定的前缀追加状态；
  * 到达 24k 上限时，按比例（如 0.67）选足最旧的完整 Turn 压缩，回落至 8k 稳固基线，开启下一轮长程高速巡航；
* 配合底层的 `ProjectionLedger` 与 Hash 锁定机制，绝不轻易篡改 System Prompt，**这正是系统在多轮高频对话中能够跑出 97%~98%+ 优异缓存命中率的核心工程基础**。

### 7. 单文件 SQLite 真相源 + Outbox 自愈
* 摆脱了对外部向量数据库（Chroma/Milvus/Qdrant）或图数据库（Neo4j）的强制依赖；
* 全部消息、摘要、关系、投影状态存储于单一 SQLite 文件，受 WAL 事务保护；
* 即使可选的向量后端故障，写操作照常提交为 `pending`，由后台 Outbox 机制自动补齐自愈，保证单体架构的高可用与稳固性。

### 8. 不假成功，不静默截断
* 压缩模型调用失败时，绝不提交空摘要，返回重试状态；
* 字段过滤不合法时，返回结构化诊断，绝不悄悄放宽成全库乱搜；
* 宁可显式报错降级，绝不把脏数据或幻觉写入长期记忆。

## 总结：系统设计的核心审美

MemCore 的全部设计，都在遵循软件工程最朴素的物理规律：

> **尊重模型算力**：把高维推理留给负责回复的模型，把繁重的时空索引交给数据库；
> **尊重物理硬件**：顺应 GPU 显存约束与云厂商 Prompt Cache 机制，不做前缀抖动；
> **尊重人机交互**：既给模型做重活的完整工具链，又给模型长期伴随的纯净工作台。

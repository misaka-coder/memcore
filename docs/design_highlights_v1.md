# MemCore 设计亮点与架构哲学 (Design Highlights & Philosophy)

> **让 AI 接着聊，也接着做事。**
>
> 本文说明 MemCore 从「长期记忆系统」演变为「上下文与记忆内核」的设计动机、关键机制与工程取舍。
> 机制以公开 API 契约为准，效果以实验与生产记录为准。

---

## 1. 为什么从「记忆系统」扩展到「上下文管理」

在传统的 Agent 设计中，「日常聊天」与「工具任务」往往是分开的两套逻辑：

* 聊天系统负责记录对话、做向量搜索；
* 工具系统负责执行、返回大段结构化输出。

但真实的长程人机交互不会这样切分。用户在一段持续会话里，随时可能从闲聊切到查资料、写代码或排障；任务完成后，又期望**在同一会话中自然继续聊天或开始下一件事**——而不是被迫开一个新窗口。

### 1.1 工具结果治理的三种取舍

面对工具调用产生的大段输出，常见处理方式有三种，各有明确代价：

| 方案 | 做法 | 代价 |
| :--- | :--- | :--- |
| **任务后移除工具轨迹** | 交付完成后，把工具调用与结果从上下文中清除 | 用户追问「刚才那个报错怎么改的」时，模型无法溯源，产生割裂感 |
| **全量保留** | 将工具调用和原始输出长期留在上下文中 | 长日志与 JSON 稀释日常对话的语义权重，提高注意力负担与账单 |
| **粗暴截断** | 取前若干字符，其余省略 | 后续真正需要核对旧细节时，信息已永久丢失 |

### 1.2 MemCore 的取向：终局结算

核心原则是**执行期完整、结束后收敛、需要时回读**：

1. **执行期（Open Turn）**：多步任务进行中，原始输出完整可见；超长内容通过分页由模型自主决定读取范围，保证推理有充分依据。
2. **终局后（Post-Terminal）**：显式启用 `compact_after_terminal` 后，成功提交 final 时把符合条件的长结果折叠为携带 `source_id`、时间与状态的确定性卡片，原文仍留存于 SQLite。**默认策略是 `full_until_raw_compaction`**，即保持完整历史直到统一 raw 压缩。
3. **保留调用行为**：调用名与参数保留在可见上下文中，模型据此辨认多份相似结果各自对应哪次执行。
4. **不做负向优化**：若正文本来就很短（低于 `operation_settlement_min_utf8_bytes`，默认 256 UTF-8 字节），或卡片无法严格节省足够字节，系统保留原文，不为压缩而压缩。
5. **按需回读**：需要旧细节时，模型调用 `open_memory(memory_id=..., view="content")` 取回正文。回读结果本身也是本轮 observation，同样遵循结算策略，不会成为新的上下文污染源。

## 2. 核心技术亮点

### 2.1 时间作为因果骨架（Time as the Backbone）

许多记忆系统把时间戳当作外围元数据，MemCore 把它提升为贯穿全局的因果骨架：

* **时序一致性**：缺乏时间参照时，模型面对堆积的事件只知道「发生过」，难以判断「何时发生」与先后顺序。
* **时区与星期感知**：系统要求有效的 IANA 时区（如 `Asia/Shanghai`），由此派生星期信息并打通三层记忆。摘要提炼会给出事件的时间跨度，系统在底层转换为标准化时间戳。
* **相对时间可解析**：配合可见的日期与星期锚点，模型能稳定解释「昨天下午」「上周二」这类表达，并据此调用 `read_timeline` 做精确核查。

源记录的时间范围由代码从记录本身计算，前提是宿主传入的时间正确；话语中描述的事件日期仍需要模型正确理解，这条边界不会被时间锚点自动消除。

### 2.2 三层记忆的用途：渐进式披露

Raw（原始层）、Episodic（阶段摘要层）、Semantic（长期事实层）不是为了分层本身而设，而是**渐进式披露（Progressive Disclosure）**的工程阶梯：

```text
               ┌────────────────────────┐
               │ 1. 标题目录 (Catalog)   │ 跨越数十天的概括，极低 Token 成本
               └───────────┬────────────┘
                           │ 模型判断相关，调用 browse / open
                           ▼
               ┌────────────────────────┐
               │ 2. 阶段摘要 (Summary)   │ 一个事件周期的事实脉络与核心结论
               └───────────┬────────────┘
                           │ 确认需要深挖字句，调用 timeline / open sources
                           ▼
               ┌────────────────────────┐
               │ 3. 原始证据 (Raw)       │ 当时原话、完整参数与执行凭证
               └────────────────────────┘
```

* **宽范围先概览**：模型可以传入横跨数周的时间范围，先浏览成本极低的标题卡片；
* **按需深入**：沿卡片附带的 ID 展开摘要正文，必要时再追溯到原始对话或工具凭证；
* **回读同样受治理**：查记忆产生的长结果本身也遵循终局结算，答完即收敛。

### 2.3 Token 做预算指标，Turn 做物理切点

按条数压缩会遇到体量极不均匀的问题；按 Token 硬切则容易切断正在进行的工具调用对。MemCore 的取舍是：

* 用 Token 衡量压力，决定**压缩多少**；
* 用完整 terminal turn 与关系组件决定**从哪里切**。

结果：上下文体积受控，同时保留的历史始终是「完整的问与完整的答、完整的 Action 与完整的 Observation」，不会拆散因果组件。计划压缩量为 `ceil(raw_token_trigger × raw_token_batch_ratio)`，比例的分母是触发阈值，而非任意时刻的积压总量；切点对齐后实际压缩量与完整轮次对齐。

包默认 `raw_token_trigger` 为 **12,000** Token、`raw_token_batch_ratio` 为 **0.67**。较大的触发线（如 24,000）可作为部署配置按需调整，但不是默认值。

### 2.4 关键词检索的三个工程闭环

MemCore 用轻量检索替代重型向量库依赖，依靠的是三个互相配合的机制，而不是「关键词够用」这一条判断。

#### (1) 联合词池（Union Pool）与多对一汇聚

* **单点打标的缺陷**：只靠原始对话提取关键词，模型遗漏元数据就会搜空；只靠阶段摘要提取，则容易丢掉具体人名、冷门项目名等细节。
* **双向互保**：系统沿血缘把原始对话的实体词与阶段摘要的主题词合并去重，经由 `get_catalog_keyword_pools` 铸成统一词池。原始层补足冷门专有名词，摘要层提供高阶概念兜底。
* **多对一汇聚**：同一话题的讨论在时序上通常密集，而数万 Token 的对话才凝练为一个阶段标题。因此底层即便命中多次具体对话，回溯到标题层时候选量通常会收敛为数量有限的紧凑卡片——底层放宽召回覆盖，顶层避免了向模型倾倒海量原始细节的扇出。

#### (2) 单向子串包含，而非全等或分词器

* **避开切分歧义**：`文旅答辩项目`、`ComfyUI本地部署` 这类复合词交给分词器容易切错；要求全等匹配则会在查询 `文旅` 时漏检。
* **匹配方向是单侧的**：系统采用 `query in stored_term` 的单向包含——短查询可以命中已存的长词条，已存的短标签不会反向匹配更长的查询。这绕开了重型分词依赖，同时能咬住专有名词的核心词根。
* 匹配是单侧的，因此**存的 `文旅答辩项目` 能被 `文旅` 命中，存的 `文旅` 不会被 `文旅答辩项目` 命中**；没有命中不等于没有历史，缺失的标签需要改用模糊检索。

#### (3) 证据回传（Witness）

命中的卡片除标题与时间外，还附带原始证据明细 `keyword_hits: [{"query": "文旅", "term": "文旅答辩项目"}]`。模型可以据此判断「这条是因为命中哪条证据被召回的」，从而决定是否下钻——这把是否展开的判断建立在可见依据上，而不是相似度分数上。

### 2.5 可见内容排除（Visible Lineage Exclusion）

把当前 prompt 中已经可见的文本再次检索出来塞进上下文，是检索设计里容易犯的错误。MemCore 在检索底层实现可见上下文差集排除：

* 当前 prompt 中已可见的近期原始对话、阶段摘要与长期事实，从候选池中剔除；
* 检索的职责是搬运模型视线之外的证据。

需要注意的是，这不等于「看到概要就看不到细节」：系统减少的是缺乏新证据的重复展示，同时保留对底层更细粒度证据的按需访问通道。

### 2.6 字节级稳定前缀与双水位线迟滞缓冲（Prefix-Cache-First & Hysteresis Buffer）

前缀缓存命中率低，通常不是因为缓存没开，而是因为前缀在每轮都被改写。固定容量的 FIFO 滑动窗口是典型原因：每进入一条新消息就从头踢出一条，历史 Token 的起始位置每轮前移，导致前缀哈希链持续偏移。

MemCore 采用**最大/最小双水位线的迟滞缓冲模型**：

* **摘要层弹性区间 `[Min, Max]`**：默认 `episodic_visible_max=8`、`episodic_compact_trigger_count=10`、`episodic_compact_batch_size=5`。在区间内只做纯尾部追加（append-only），已有历史在字节级别保持稳定；蓄满触发数才压缩最旧一批。
* **Raw 对话层的 Token 差值蓄水池**：从基线到触发阈值之间是一段只追加的稳定期，达到阈值才集中整理最旧的完整 turn，再回落到基线。默认阈值 12,000 Token、比例 0.67。
* 配合 `ProjectionLedger` 与 hash 锁定，已冻结的 provider 投影不会被静默重写。

前缀变动的频率因此被稀释到约 $\frac{1}{\text{Max} - \text{Min}}$。**这是前缀可证明稳定的机制保证，不是对 provider 缓存行为的承诺**——最终 hit/miss 仍取决于 provider 的缓存策略、模型版本与请求顺序。缓存命中率也不能单独作为优化目标：保留大量无用历史同样能提高命中率。

在生产部署中，该系统录得约 97%~98% 的输入缓存命中率（口径：命中输入 tokens 总和 ÷ 总输入 tokens 总和）。这是该部署的观测值，不是可移植的承诺。

### 2.7 单文件 SQLite 真相源与 Outbox 自愈

* 不强制依赖外部向量数据库或图数据库；
* 全部消息、摘要、关系与投影状态存储于单一 SQLite 文件，受 WAL 事务保护；
* 即使可选的向量后端故障，写操作仍照常提交并把索引操作保留为 `pending`，由后台 Outbox 机制在恢复后通过 `reindex_pending()` 补齐；
* `reindex_all()` 可从 SQLite 真相源重建当前 hard namespace 的索引。SQLite 是事实源，向量索引只是检索加速层。

### 2.8 结构化状态，不假成功

* 摘要模型调用失败时不提交空摘要，返回重试/延迟状态；
* 索引失败或并发冲突返回结构化状态，不伪造成功；
* 非法过滤条件返回结构化错误，不静默放宽成全库搜索；
* 坏 JSON 不会被当作有效 speech 或记忆提交。

---

## 3. 设计取向小结

MemCore 的设计围绕三条约束展开：

> **把推理留给模型**：高维判断交给负责回复的模型，时空索引与状态一致性交给存储层；
> **顺应缓存机制**：让已稳定的前缀尽量保持字节不变，避免无必要的历史改写；
> **兼顾两种连续性**：既让模型在做重活时拿到完整证据，也让长期聊天拥有干净的工作台。
